## 1. 原始需求复述

> 我希望后台能够记录历史数据，结构化的非结构化的，这样通过定时拉取信息就可以丰富我的工作台信息，你需要设计相关的数据库结构，满足我的办公需求。

**需求解读**：现状是「工作台只能看到最新一天的快照」（`console` 纯读 `data/reports/daily_scan/<日期>/` 的本地文件）。用户要的是把每天定时拉取的结构化/非结构化信息**沉淀成可查询的历史库**，让工作台从「单日快照」升级为「可回溯的历史视图」。

## 2. 产品目标

| # | 目标 | 说明 |
|---|---|---|
| G1 | **可回溯** | 让控制台从「只读最新一天」升级为「可查询任意历史日」——补齐时间维度 |
| G2 | **可检索** | 把散落在 `data/`（reports 79 MB）里的结构化/非结构化信息，统一沉淀为可 SQL 查询 + 可全文检索的单一数据源 |
| G3 | **可监控** | 让「采集停更 33 天」「最新一天残缺」这类问题**可被系统发现**，而不是靠人肉翻目录 |

> 三个目标正交：G1 是时间轴、G2 是内容轴、G3 是质量轴。

### 2.1 已确认的决策约束（不可推翻）

| 决策 | 内容 |
|---|---|
| D1 选型 | **DuckDB 单文件**，随项目走、零运维、不引入服务端 |
| D2 回填 | **全部回填**：9 个扫描日的 800 币快照 + 455 条深度研究 + 19 个宏观日的全部快照 |
| D3 场景 | **四大办公场景全做**：币种历史趋势 / 叙事与新闻时间线 / 采集健康度监控 / 历史快照回溯 |
| D4 非结构化 | **原文留档 + 全文检索**：可直接搜新闻/帖文正文关键词 |

## 3. 用户故事

### US-1 币种历史趋势（场景：D3-①）

> **作为**投研分析师，**我希望**能查询任一币种在全部历史日期的价格/市值/排名/评分/社交热度序列，**以便**判断趋势，而不是只看当下。

**验收标准**
- [ ] 给定 `coin_id` + 时间范围，返回**按日期升序**的时间序列，每个有数据的日期一条记录
- [ ] 单币可返回的指标 ≥ 5 个：`price_usd`、`market_cap`、`rank`、`score/sentiment`、社交热度
- [ ] 序列中的**缺失日必须显式标记为 gap**，不得插值或前向填充（数据可信度优先）
- [ ] 支持在同一图表中叠加 ≥ 2 个指标
- [ ] 回填后，币种的最大可回溯跨度 = 9 个扫描日（2026-06-27 ~ 2026-08-26）

### US-2 叙事与新闻时间线（场景：D3-②）

> **作为**研究员，**我希望**看到题材热度随时间的演变，以及每个时点当时出现过哪些新闻/帖文，**以便**复盘叙事是如何发酵的。

**验收标准**
- [ ] 可按 `category`（layer-1 / defi / meme / rwa / stablecoin / layer-2 / exchange / ai / unclassified）查询各扫描日的币种数量与热度变化
- [ ] 可按日期区间列出该窗口内的新闻条目标题 + 来源 + 时间戳，跳转回原快照
- [ ] 时间线条目能定位到「当时关联的币种」与「当时的原始文件路径」
- [ ] 覆盖 455 条深度研究内的全部 `crypto_news` / `rss` / `v2ex` / `reddit` 内容源

### US-3 采集健康度监控（场景：D3-③）

> **作为**运维者，**我希望**看到各数据源的成功率、缺失日与 confidence 水平，**以便**第一时间发现采集异常。

**验收标准**
- [ ] **单日视图**：每个源返回 `ok` / `error` 计数与成功率
- [ ] **趋势视图**：按日聚合的成功率序列（含 confidence 均值/分布）
- [ ] **缺失日列表**：能列出扫描日与宏观日的所有数据空洞（gap）
- [ ] 能复现异常 A：`2026-08-26` 仅 4 条 detailed（正常日 50–66 条）
- [ ] 能复现异常 B：`daily_scan` 停更约 33 天（最后写入 2026-08-26），而 `macro` 仍有到 2026-09-27 的快照 → **分源断更应该被区分标示**
- [ ] 能识别 schema 漂移：源数量在不同日期为 13 或 14（见附录 A.2）

### US-4 历史快照回溯（场景：D3-④）

> **作为**用户，**我希望**能选择任意历史日期把工作台还原成那天，**以便**复现当时的决策上下文。

**验收标准**
- [ ] 各端点支持 `?date=YYYY-MM-DD`
- [ ] 新增「可用日期列表」能力，供前端日期选择器渲染
- [ ] 选中**残缺日**时给出明确提示（如「该日仅 4 条深度研究」），而不是展示空白档案
- [ ] `latest` 解析**不再自动落到残缺日**（当前 `resolve_scan_date` 取字典序最大目录，会命中 2026-08-26）
- [ ] 回溯切换不改变页面的信息层级，仅数据换天

### US-5 非结构化全文检索（场景：D4）

> **作为**研究员，**我希望**直接搜新闻/帖文正文关键词，**以便**找到曾经提到某币/某事件的原始记录。

**验收标准**
- [ ] 输入关键词（含中文），返回命中条目：正文片段 + 来源源名 + 日期 + 关联币种
- [ ] 命中结果支持按日期区间、币种、源类型过滤
- [ ] 每条命中可回溯到原始文件路径（原文留档）
- [ ] 检索覆盖 `crypto_news` / `rss` / `reddit` / `v2ex` / `bilibili` 的正文

## 4. 需求池

优先级定义：**P0 = Must have（不做则价值不成立）** / **P1 = Should have** / **P2 = Nice to have（可延后）**

### P0（8 项）

| ID | 需求 | 说明 / 验收口径 |
|---|---|---|
| **R1** | 历史数据一次性回填（ETL） | 导入 9 扫描日 × 800 币轻量快照 + 455 条深度研究 + 19 宏观日全部快照；可重复执行 |
| **R2** | 幂等写入 | 以自然键（`date` + `coin_id` 等）UPSERT；同一批数据执行 N 次，行数不增、不产生重复 |
| **R3** | 结构化时间序列主表 | 行情快照（800/日）与宏观快照的可查询时间序列，支撑 US-1 / US-4 |
| **R4** | 数据源状态事实表 | 逐日 × 逐币 × 逐源记录 `status` / `error` / `confidence` / `timestamp`，支撑 US-3 |
| **R5** | 原文留档 + 全文检索 | 非结构化正文落库留档并建全文索引，支撑 US-5 |
| **R6** | 历史日期回溯 | 端点 `?date=` 支持任意历史日 + 可用日期列表接口，支撑 US-4 |
| **R7** | 残缺日识别与处理 | 定义「残缺日」判定口径，`latest` 解析跳过残缺日并给出提示 |
| **R8** | 兼容现有 10 个端点 | **不得破坏现有响应契约**（信封 `{code, message, data}` 不变），前端零改动或最小改动即可跑通（详见 §6） |

### P1（5 项）

| ID | 需求 | 说明 |
|---|---|---|
| **R9** | 定时增量入库 | 与现有守护进程/cron 的关系需先定（见 Q1）；建议复用现有调度，不新增常驻服务 |
| **R10** | 健康度统计与告警 | 成功率跌破阈值 / 出现新缺失日 / 分源断更超 N 天时给出告警 |
| **R11** | `raw_server` parquet 处置 | 5 个源、每文件仅 1 行，`github` 84 列几乎全为无用 URL 模板 → **建议标注「暂不入库」并说明理由**，不为它迁就 schema |
| **R12** | `by_category` 冗余去重 | `by_category/<slug>/<coin_id>.json` 与 `top_50_detailed` 同内容 → **只入库一次**，避免体积翻倍 |
| **R13** | 数据保留与增长策略 | 按 §5 测算设定保留窗口与 volume 预警线 |

### P2（3 项）

| **R16** | 跨源交叉验证 | 同一币种在多源（market 快照 vs 宏观 watchlist）的一致性核对 |

## 5. 数据保留与增长测算

### 5.1 回填基期（一次性，实测口径）

| 数据源 | 量级 | 体积 |
|---|---|---|
| 轻量行情快照 | 9 日 × 800 币 ≈ **6,750 行** | ≈ 2.9 MB JSON |
| 深度研究 | **455 条**（9 日） | ≈ 62.6 MB JSON |
| 宏观快照 | **45 个**（19 日） | 0.54 MB |
| **合计** | **≈ 7,250 行主记录 + 数万条子行** | **≈ 66 MB JSON 源** |

> 注：`data/` 实测总体积 **87 MB**（其中 `data/reports/` 79 MB），含 `by_category` 冗余副本与 cache。

### 5.2 单日增量（采集恢复、正常运行）

| 数据源 | 每日行数 | 每日体积 | 说明 |
|---|---|---|---|
| 轻量快照 | ~750 行（800 中约 750 有效） | ~330 KB | 强结构化，schema 稳定 |
| 深度研究（主记录） | ~55 条（正常日 50–66） | ~7.5 MB | 含 13–14 源聚合 |
| ├─ 源状态子行 | ~55 × 14 ≈ **770 行** | — | 逐源 status/confidence |
| ├─ 新闻/文章子行 | ~55 × 80 ≈ **4,400 行** | — | 正文体积的大头 |
| └─ 帖子子行（reddit） | ~55 × 20 ≈ **1,100 行** | — | 非结构化正文 |
| 宏观快照 | 实测 2–6/日，设计上限 24/日 | ~30–290 KB | 列表型子表需拆子表/JSON |
| **合计** | **≈ 7,500 行/日** | **≈ 8.1 MB/日** | 行数主要被新闻/帖子占据 |

### 5.3 一年后规模推演

| 口径 | 一年（365 日） |
|---|---|
| 主记录行数 | ≈ 750×365 + 55×365 + 24×365 ≈ **30.3 万行** |
| 全部行数（含子表/全文） | ≈ **270 万行** |
| 原始 JSON 体积 | ≈ 8.1 MB × 365 ≈ **2.96 GB** |
| DuckDB 单文件（列式压缩后） | **≈ 0.6 – 1.0 GB**（文本类 JSON 通常 4–8× 压缩，含 FTS 索引开销） |

**结论**：DuckDB 单文件完全撑得住。
- 单文件 1 GB 量级，在 Windows 本地读写无压力，随项目 git 外挂即可（应列入 `.gitignore`，见 Q5）；
- 若只保留近 180 天滚动窗口，稳态体积可压到 **0.3–0.5 GB**；
- **风险点不在容量，而在采集是否恢复**——当前 `scan` 已停更 33 天，若不修复，增量为 0，历史库只增不回填。

## 6. 与控制台现有端点的兼容策略（关键约束）

**现状（已实测）**：后端 `console/backend/` 共 **10 个端点**，统一信封 `{code, message, data}`：

| # | 端点 | 与历史库的关系 |
|---|---|---|
| 1 | `GET /api/health` | 保持原样 |
| 2 | `GET /api/meta` | 保持原样 |
| 3 | `GET /api/market/overview` | 可接历史日 |
| 4 | `GET /api/macro/btc-dominance` | 可接历史日 |
| 5 | `GET /api/onchain` | 保持原样 |
| 6 | `GET /api/opportunity/radar` | 可接历史日 |
| 7 | `GET /api/score/{coin_id}` | 可接历史日 |
| 8 | `GET /api/tokens/{coin_id}` | 已支持 `?date=`（见下） |
| 9 | `POST /api/tokens/{coin_id}/research` | 保持原样（实时抓取） |
| 10 | `POST /api/comparison` | 可接历史日 |

**关键事实**：`console/backend/core/paths.py::resolve_scan_date` 已支持 `?date=` 参数（非空且非 `latest` 时原样返回），且 `GET /api/tokens/{coin_id}` 已声明 `date` 查询参数 → **历史回溯的管道已部分存在，缺的是「数据源从文件换成 DuckDB」这一层**。

**兼容原则（硬性）**
1. **响应契约零破坏**：`data` 的字段名、层级、类型不变；信封 `{code, message, data}` 不变。前端已按现有结构渲染，不得要求前端大改。
2. **读路径可切换**：新增仓储层作为唯一数据入口，先「文件直读」后「DuckDB 读取」，两者产出同一 `data` 结构，便于灰度与回退。
3. **兜底不报错**：沿用既有约定——数据缺失返回空结构 + 非 0 code，**绝不抛 500**。
4. **增量能力走新增端点**：历史趋势 / 全文检索 / 健康度属于新能力，以**新增端点**提供，不修改老端点语义。
5. **`latest` 语义修正需向后兼容**：修正「latest 落到残缺日」时，通过 R7 的跳过规则实现，老客户端传 `latest` 时行为改善但不报错。

## 7. UI 设计草案（基础布局）

沿用控制台深色科技风，不新增独立应用，只在现有工作台上叠加**时间维度**。

```
┌─────────────────────────────────────────────────────────┐
│  claude_trading 投研控制台            [日期: 2026-08-25 ▾]│  ← 全局日期选择器（新增）
├──────────────┬──────────────────────────────────────────┤
│ 侧栏导航      │  ① 概览卡片（随所选日期刷新）             │
│  · 概览       │    市值 / 涨跌 / 恐惧贪婪 / 采集健康徽章   │
│  · 币种档案   │                                          │
│  · 趋势       │  ② 趋势区（US-1）                        │
│  · 时间线     │    指标多选 + 折线，缺失日显式空心断点      │
│  · 健康度     │                                          │
│  · 检索       │  ③ 叙事时间线（US-2） 横向时间轴 + 新闻卡 │
│  · 回溯       │                                          │
│              │  ④ 健康度面板（US-3） 源成功率热力 + 缺口表 │
│              │                                          │
│              │  ⑤ 全文检索（US-5） 关键词 + 日期/币种过滤 │
└──────────────┴──────────────────────────────────────────┘
```

**交互要点**
- 日期选择器只列出**可用日期**；残缺日带 ⚠ 标记，选中时顶部提示「该日深度数据仅 4 条」
- 所有图表对 gap 用空心点/断线表示，**不做插值**
- 健康度面板对「分源断更」用不同颜色区分（scan 停更 vs macro 正常）
- 全文检索结果每条带「原文路径」，可复制回原始文件

## 附录 A：数据现状事实清册（实测，作为建模输入）

### A.1 三类数据形态

| 类别 | 路径 | 结构判定 | 关键事实 |
|---|---|---|---|
| **A 轻量行情快照** | `data/reports/daily_scan/<日期>/top_800_light/all_coins.json` | **强结构化** | `list[800]`，13 字段完全稳定；空值率实测：`max_supply` 319/800、`change_24h_pct` 19/800、`rank` 3/800、`change_7d_pct` 5/800 |
| **B 深度研究** | `data/reports/daily_scan/<日期>/top_50_detailed/<coin_id>.json` | **半结构化** | 单币一份，聚合 13–14 个源；异构严重；大量源失败（实测 `market` 返回 `429`、`community_score` 触发 `'str' object has no attribute 'get'`） |

| **D 原始 parquet 副本** | `data/raw_server/<source>/<日期>.parquet` | **基本无价值** | 5 源（coingecko/coinglass/defillama/github/reddit），每文件仅 1 行；`github` 84 列几乎全为 URL 模板 → **建议 R11 暂不入库** |

### A.2 源列表存在 **schema 漂移**（建模必须按稀疏处理）

| 日期 | detailed 文件数 | 源数 | 备注 |
|---|---|---|---|
| 2026-06-27 / 28 / 29 | 50 / 50 / 50 | **13** | 无 `github` |
| 2026-06-30 | 66 | **14** | 起多出 `github` |
| 2026-07-01 / 02 / 03 | 61 / 60 / 59 | **14** | |
| 2026-08-25 | 55 | **14** | |
| 2026-08-26 | **4（残缺）** | **13** | 又无 `github` |

> **结论**：源集合不是固定 13 个，跨日期在 13 / 14 之间漂移（`github` 源时有时无）。**源状态表必须按稀疏长表建模**（`date × coin × source`），不能用固定列，否则 schema 一改就崩。
